# Mindbody API-key-only customer checkout: validation evidence

Researched: 2026-07-21  
Scope: official Mindbody developer/support material only. This supplements [the v1 capability research](mindbody-v1-capabilities.md). It does not authorise a production payment implementation.

## Result

The official material establishes that the Public API can complete sales and that `CheckoutShoppingCart` is an **integration-driven** checkout endpoint. It does **not** establish a general Mindbody-hosted checkout page, a supported test-card data set for the Public API sandbox, or Revvi's PCI/card-data scope. Those three gaps remain a Mindbody API Support and pilot-Business validation gate.

The Mindbody Affiliate API is designed for customer find/book/pay journeys, but it is **not** the requested API-key-only route: it requires an API key *and* Basic authentication made from a back end, and its documented booking request contains a full PAN and CVV. It therefore cannot be substituted silently for Revvi's API-key-only Public API design. [Affiliate API: purpose and onboarding](https://developers.mindbodyonline.com/AffiliateDocumentation), [Affiliate API: authentication](https://developers.mindbodyonline.com/AffiliateDocumentation).

## Evidence and implications

| Question | Official evidence | Planning conclusion |
| --- | --- | --- |
| Is there an API-key-only customer booking/payment flow proved for Revvi? | The Public API endpoint catalogue lists appointment booking and completing service/product purchases. The Public API setup flow grants Revvi access to a Business through Site Activation. However, the reviewed published material does not show the authenticated `CheckoutShoppingCart` request schema or say that it is a customer-booking flow with API key alone. | Keep the intended Public API route as a hypothesis, not an implementation decision. Ask Mindbody whether `AddAppointment` plus `CheckoutShoppingCart` supports an API-key-only, customer-present appointment sale for each activated Business. [Public API endpoint catalogue](https://developers.mindbodyonline.com/Resources/Endpoints), [Public API getting started](https://developers.mindbodyonline.com/ui/documentation/public-api) |
| Is `CheckoutShoppingCart` a hosted checkout with a normal return URL? | Mindbody describes SCA additions to `CheckoutShoppingCart`: an integration sends `PaymentAuthenticationCallbackUrl`; a bank may return `AuthenticationUrl`; the consumer is redirected back only after the bank challenge; the integration must then call `CheckoutShoppingCart` again with `TransactionIDs` to capture funds. | No. The callback is an SCA-bank-challenge return, not evidence of a hosted Mindbody checkout or a completed Booking. Revvi must persist the pending transaction state, verify the second checkout response, then reconcile the Booking. [SCA release notes](https://developers.mindbodyonline.com/Resources/ApiReleaseNotes) |
| When can a Business process cards? | Mindbody's FAQ says API card processing requires the studio in the request to have an active Mindbody merchant account. It names TSYS, Bluefin, Elavon, Paysafe, Ezidebit, and Adyen as API-supported processors, and limits availability by country/processor. | Validate merchant account and supported payment methods for **every Business** before enabling paid Booking. A successful sandbox call is insufficient proof. [Mindbody API FAQ](https://developers.mindbodyonline.com/resources/faqs) |
| Can we test checkout without real card data? | Mindbody release notes show `CheckoutShoppingCart` has a `Test=true` mode (including a fixed `Test=true`/`InStore=true` response issue). Public-sandbox testing is free and rate-limited; a custom sandbox provides more control over its Business data. The reviewed official Public API material does not publish supported test PAN/CVV/expiry values or state exactly which checkout/payment combinations test mode accepts. | Use `Test=true` only after Mindbody confirms the exact request contract and supplies supported test data. Do not use a real card or invent a test PAN. [Checkout test-mode release note](https://developers.mindbodyonline.com/Resources/ApiReleaseNotes), [sandbox FAQ](https://developers.mindbodyonline.com/ui/faq), [API FAQ](https://developers.mindbodyonline.com/resources/faqs) |
| Who handles PCI and card data? | Mindbody's API Terms prohibit caching over 48 hours, collecting, compiling, storing, transferring, or using Mindbody-derived data, explicitly including cardholder data and addresses. The reviewed Public API sources require TLS 1.2+ and identify that requirement as part of Mindbody's PCI compliance, but do not allocate PCI DSS responsibilities between an integration and Mindbody. The separate Affiliate API's documented customer-payment request includes `creditCardNumber` and `creditCardCVV`; it also requires API key plus client-key/client-secret authentication. | Do not log, store, or persist cardholder data in Revvi. Do not collect or transmit it for the Public API route until Mindbody provides the supported payment contract and a written PCI responsibility position. Treat Affiliate API examples as evidence of a different, credentialed product—not approval to use raw card data in the Public API route. [Mindbody API Terms](https://developers.mindbodyonline.com/Resources/DeveloperAgreement), [TLS/PCI release note](https://developers.mindbodyonline.com/Resources/ApiReleaseNotes), [Affiliate booking request](https://developers.mindbodyonline.com/AffiliateDocumentation) |
| Can Mindbody deliver Revvi-branded transactional notifications? | Mindbody release notes say appointment confirmation emails are sent when enabled by studio settings, and class confirmation email/SMS is triggered by `SendEmail=true`. The reviewed Public API reference does not document a request field or endpoint to choose an email/SMS template, sender, logo, or brand. | Configure and acceptance-test the Business's Mindbody settings: recipient, channel, sender, copy, and Revvi-approved branding. Do not promise API-controlled branding. [2026 notification release notes](https://developers.mindbodyonline.com/Resources/ApiReleaseNotes) |

## Required validation questions for Mindbody API Support / pilot Business

1. For an activated Business using only Revvi's Mindbody API Key and Site ID, which Public API calls create a customer Booking and collect its payment without staff credentials or a user token?
2. What exact `CheckoutShoppingCart` request fields and payment types are allowed for that route, and must the appointment be created before or after the sale?
3. Is `Test=true` supported for that route in the public or custom sandbox? Provide the official test payment data and expected non-production outcome.
4. For each pilot Business, is its merchant account active and processor/payment-method combination API-supported?
5. For SCA, what state must Revvi retain, what should Revvi do after callback, and what response or webhook establishes completed payment and Booking?
6. Does this route ever require Revvi to receive PAN/CVV? If yes, what PCI DSS responsibilities and approved collection pattern apply? If no, what supported token/hosted/payment-method mechanism replaces it?
7. Which Mindbody Business settings control booking confirmation, receipt, sender, and email/SMS branding, and can the pilot Business demonstrate the required Revvi-branded notification?

## Source notes

- The published Public API endpoint catalogue establishes capability categories, not a detailed checkout contract. [Endpoints](https://developers.mindbodyonline.com/Resources/Endpoints)
- The FAQ's processor statement and the 2019 release note's statement that ACH/direct debit was added conflict. Because both are official but time-separated, obtain the current per-Business payment-method answer from Mindbody rather than treating either as universal. [API FAQ](https://developers.mindbodyonline.com/resources/faqs), [API release notes](https://developers.mindbodyonline.com/Resources/ApiReleaseNotes)
