# Mindbody capabilities for the Revvi v1 booking model

Researched: 2026-07-20  
Scope: official Mindbody developer and support documentation only.

## Decision summary

Mindbody's Public API supports the core data and booking operations needed for a multi-business Revvi integration: a developer application is activated per Mindbody business (Site ID), locations are exposed under the site, and the API has endpoints for services, appointment availability, clients, appointments, and sales. It therefore supports a Revvi server-side integration with a per-business credential/activation record.

The evidence **does not establish a general Mindbody-hosted checkout page** that accepts a return URL and completes a normal appointment payment. The documented Public API model is integration-controlled checkout (`CheckoutShoppingCart`), with a limited bank/SCA authentication redirect for relevant payment methods. Treat a fully hosted Mindbody checkout-and-return experience as an unresolved product/technical decision that must be validated with Mindbody before it is committed to v1.

Mindbody confirmation emails/SMS can be triggered by booking calls when enabled, but the material reviewed does not demonstrate that API clients can set or select an email template/brand. Revvi-branded messages should therefore be configured and verified in each Mindbody business, rather than assumed to be API-controlled.

## Important constraints to carry into the specification

1. **A business is not necessarily a location.** Mindbody's Site ID may cover several locations; Revvi needs separate tenant and location concepts.
2. **Credentials require a commercial/onboarding flow.** Production access requires Mindbody approval and a business-specific activation process. Manual Revvi onboarding is compatible with that requirement.
3. **Availability must remain live.** Displayed availability is advisory until Mindbody accepts the booking.
4. **Memberstack identity alone is insufficient.** A tenant-scoped Mindbody client mapping and duplicate-safe creation flow are needed.
5. **Payment is the primary unresolved risk.** The Public API supports checkout and limited authentication redirects, but the requested hosted Mindbody checkout/return flow is not established by the official material reviewed. Resolve it with Mindbody API Support before implementation tickets commit to it.
6. **Mindbody owns notification delivery, but branded content must be operationally verified.** Do not promise Revvi-branded transactional messaging until a test business confirms Mindbody template/customisation capability for the intended account plan and channel.

## CheckoutShoppingCart clarification

The linked V6 `CheckoutShoppingCart` documentation is rendered in Mindbody's developer portal and was not available as static endpoint text. Mindbody's official release notes nevertheless make the integration model clear: checkout is API-driven, and the integration is responsible for sending the checkout request and completing it after any SCA challenge. `PaymentAuthenticationCallbackUrl` only provides the return from a bank authentication challenge; it is not evidence of a general Mindbody-hosted checkout page.

Mindbody also announced in June 2026 that Apple Pay is available to Public API integrations through its existing alternative-payments checkout flow (payment-method ID `801`). That establishes a possible payment method, but does not by itself settle Revvi's card-data, PCI, product-access, or customer-experience responsibilities. Those remain pilot-validation gates.

## Sandbox environment

Mindbody's Public API documentation says its sandbox is for application development and testing. The official FAQ distinguishes the free public sandbox from a paid custom sandbox Site: the custom option provides control and flexibility over the business data. The free sandbox is sufficient to exercise supported API flows, subject to its documented call limits; it is not proof that a production Business will have the required payment configuration or notification branding.
